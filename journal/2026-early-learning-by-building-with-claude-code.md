# Learning by building with Claude Code

**Period:** Early 2026 onward  
**Theme:** learning, agentic development, problem-solving

I discovered Claude Code around nine months before starting this journal. Since then, I've used it almost every day. I took courses to fill gaps, but the bigger change came from trying to build things and having to understand why they worked—or why they didn't.

Before that, I had worked across a fairly unusual range of jobs: construction sites, gaming lounges, teaching board games, phone retail, content creation, technical support, community leadership, QA, esports casting, and baking. Those jobs aren't a conventional route into software or AI. They did, however, make me comfortable entering unfamiliar environments, noticing how people actually use a system, and asking questions until I understand the problem.

Claude Code gave me a way to turn that habit into practical technical work. I began making small tools for my own workflow, including a terminal status line and thread-based ways of organizing agent work across sessions. I found that the interesting part wasn't simply asking an agent to write something. It was learning to describe the desired behavior, inspect what it changed, notice what it misunderstood, and build a way to verify the result.

That process changed how I think about my own ability. It helped me discover a problem-solving side of myself that I had wanted to develop for a long time. It also made the gap between an idea and a working prototype feel more approachable—but not effortless. The work still depends on judgment, careful questions, and checking what actually happened.

One thing I try to keep in mind: being able to generate code quickly is not the same as understanding a system. I want to understand enough to identify weak assumptions, recognize when an agent has gone off track, and know what evidence would convince me that a change is correct.

## What I'm taking forward

- Treat agent output as a proposal to inspect, not as proof.
- Learn by building something concrete, then tracing its behavior.
- Keep requirements and acceptance criteria visible instead of relying on conversational memory.
- Use tests and direct inspection to distinguish a plausible explanation from a verified result.

This is still a learning process. The goal of the journal is to record that process honestly, including the parts I have not figured out yet.
